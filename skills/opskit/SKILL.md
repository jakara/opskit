# OpsKit 打包与交付

## 开始先选择模式

在检查业务仓库、生成配置、收集依赖或调用 Docker 前，先问用户：“是否直出 OpsKit？”并给出两项：

- **是，直出 OpsKit**：只打包 OpsKit 管理端、采集端、安装入口和内置说明，不包含业务应用、容器镜像或离线系统依赖。
- **否，制作完整气隙包**：适配业务仓库，收集镜像和离线依赖，完成隔离验收后封包。

等待用户选择后再执行对应流程，不用沉默或超时替用户选择。本次任务已经明确选择直出或完整气隙交付时，说明采用该模式即可，不重复询问。

## 直出 OpsKit

选择直出后，使用 Skill 自带的固定快照运行：

```text
python3 <技能目录>/scripts/export_opskit.py --output <交付目录>
```

交付 `opskit-direct.tar.gz` 和同名 `.sha256` 文件；包内包含 `opskit/`、全部快照文件、来源记录 `OPSKIT_SOURCE.json` 和文件校验清单 `SHA256SUMS`。脚本校验快照、按清单复制文件，排除未登记的本机配置和数据，拒绝覆盖已有包。

直出无需业务仓库、`opskit-delivery.json`、Docker 或完整气隙验收；不运行下面的气隙流程。打包完成后核验归档校验和、解压后的文件清单和可执行权限。向用户说明：这是 OpsKit 独立安装包，未携带镜像及离线依赖；首次安装按包内说明联网准备依赖和镜像，不能称为已验收的气隙包或已部署服务。

## 完整气隙交付

以下流程仅在用户选择完整气隙包后执行。

将当前业务仓库变成一个初级现场工程师可使用的离线交付包：解压、运行 install.sh、选择本机角色、填写中文表单，按已编制的 Spug 操作手册完成后续升级。交付包同时携带业务应用和 OpsKit 管理端/采集端，现场不拉代码、不构建、不下载镜像或依赖。

制包工作由本 Skill 在联网开发环境完成。当前现场目标是 Anolis OS 8.9 / 8.10，amd64 / arm64；制包端可使用具备 Python 3.9+、Docker、Compose 和 Buildx 的 Linux、macOS 或 Windows。其他现场系统需先完成对应依赖收集器和离线验收，不能改一个 target 字段就宣称支持。

## 获取真实部署输入

先读取仓库规则、现有 Dockerfile/Compose、部署与升级说明、配置模板、数据模型和验收方式。运行：

```text
python3 <技能目录>/scripts/build_bundle.py inspect --repo <业务仓库>
```

优先复用已有部署资源。缺 Dockerfile/Compose 时，在用户授权的交付范围内结合真实启动方式补齐；应用自身不支持容器或缺关键部署信息时，明确具体缺口，不生成能启动空容器的替代系统。示例目录只用于演练，不能替代客户应用。

目标系统、CPU 架构、业务版本、主机角色能从用户和仓库推断时直接采用并说明；只有决定不了时才集中询问缺项。不要要求用户逐步批准常规适配。制包授权不包含推送仓库、发布镜像或操作客户服务器。

按 [交付契约](references/bundle-contract.md) 在业务仓库写入 `opskit-delivery.json`：

- 每个角色明确部署项目名、Compose、所需资源、中文参数及业务检查。主机 IP、密码和连接配置留在现场输入，发行包只带参数定义。
- 构建镜像必须指定目标平台，所有服务都要有可导出的镜像。构建前核对 `.dockerignore`、secret build 参数和镜像环境变量，不能将开发 `.env`、SSH 私钥、客户数据或凭据烘焙进去。
- Compose 不依赖制包机绝对路径；将必要非敏感资源作为显式 files。真实 `.env`、未声明 env_file、仓库外目录或缺失的文件不能悄悄忽略。
- 有数据库、持久卷或可写业务目录时，给出真实备份动作。数据库迁移由应用现有工具或适配脚本执行，必须根据兼容性选择 app-only / restore-hook / unsupported 回退策略；不能将换旧镜像当作数据库回退。
- hooks 在制包阶段写好并测试。禁止把“TODO”、空脚本、`exit 0`、提示现场自行填写的命令作为完成的备份、迁移或检查。
- 将应用专有的部署顺序、外部依赖准备、参数示例和业务成功判据写入各角色 `site_notes`。制包器把它们生成到中文现场手册，封包后不要求驻场工程师继续编写。
- 将开发者明确指定的交付文件/目录写入顶层 `documents` 字符串数组，路径相对当前业务仓库。未指定时优先采用已有对外交付目录，先检查是否含实际密码/客户数据；不能把整个仓库当文档打包。Markdown 的相对图片及关联资料一并选择，保留相对路径。支持 Markdown、文本、PDF、Word `.docx` 和常见图片；旧 `.doc` 或其他格式应在制包阶段转成支持格式，不把转换任务留到现场。

## 将文档放进工作台

制包器会将自动生成的现场/Spug 手册、OpsKit 内置说明及 `documents` 中的资料编译到 `opskit/management/documents/`，按交付手册、项目文档和内置说明分组。它们是普通文件，可用 vim 查看；管理端安装后可从 Hub 首页搜索、预览和下载原件。Markdown 和 Word 渲染资源随包携带，不调用 Office 云服务或外部 CDN。

在隔离验收中实际打开 Hub 文档中心：检查全部应交资料在列表出现、中文文件名可读取、Markdown 的表格/代码/相对链接/图片可用；如有 Word，验证正文、表格和嵌入图片能显示。Word 复杂排版可下载原件核对，不能把只看到文件名算预览通过。确保仅选择发布资料，文档预览不能读取系统文件、凭据或执行文档脚本。

新版本还需在管理机发布文档：按生成手册运行 `--role management --action sync-docs`，必要时用 `--documents-dir` 指向已有 Hub 文档库。业务主机升级不代表管理机资料已更新。文档同步须保留其他应用/手工文档，覆盖本应用旧文档前备份并校验，本地修改冲突停止处理；这一步不升级 OpsKit 本体。

## 准备真正的离线输入

按 [依赖收集说明](references/prerequisites.md) 收集并验证对应 OS/CPU 的完整 RPM 闭包。可复用同目标的已验证依赖目录，复用前核对 manifest 和每个文件哈希。

```text
python3 <技能目录>/scripts/collect_prerequisites.py --os anolis --version 8.9 --arch amd64 --output <工作目录>/prerequisites
```

该操作使用一次性目标容器，不修改制包机的软件源和已装依赖。必须在另一个干净目标容器禁网安装验证成功。基础依赖包含并行 Python、Docker/Compose、监听查询工具，现场保留系统 Python，不通过强制卸包解决现有运行时冲突。

构建业务镜像并保存固定版本。远程镜像由制包器锁定目标平台 digest 后导出；本地构建镜像可用 `--use-local-images`，仍须验证架构。不得将 ARM Mac 默认镜像当作客户 x86 镜像。业务、OpsKit 管理组件和 Fluent Bit 都必须齐全。

```text
python3 <技能目录>/scripts/build_bundle.py build --repo <业务仓库> --config <业务仓库>/opskit-delivery.json --output <暂存目录> --prerequisites-dir <工作目录>/prerequisites
```

在 OpsKit 工程中执行时使用当前运行源码；独立分发的 Skill 自动使用 `assets/opskit` 固定快照。必要时通过 `--opskit-source` 显式选择可信版本。快照、镜像 ID、目标平台和业务版本必须写入交付记录。

## 隔离验收后再封包

`build` 产物是暂存目录，不是正式交付包。依据 [验收与现场手册要求](references/acceptance.md)，在干净的同架构 Anolis VM 或容器中断网执行：

1. 从缺 Python/Docker 的基线验证本地依赖安装，检查目标不匹配和损坏包会提前失败。
2. 在隔离项目、端口及数据目录中分别安装 OpsKit 管理端和 Fluent Bit，确认初始化、入口及真实日志写入；不得借用或更改原有生产实例。
3. 按每个业务角色填写现场参数，安装并执行真实业务检查。有状态角色还要验证备份产物能恢复到隔离数据集。
4. 对涉及升级的交付验证前版到本版，以及声明支持的回退路径。失败停止后续主机，不能通过忽略退出码或降低健康标准来封包。

记录实际命令、结果、目标环境、无外网条件和测试覆盖，生成与 artifact_id 绑定的验收 JSON。容器验收不等于 VM 的 systemd、内核、SELinux 或重启验收；必须在报告中区分。无法访问真实客户设备不要求操作生产环境，交付时如实说明尚需现场验收的项目。

```text
python3 <技能目录>/scripts/build_bundle.py seal --bundle <暂存目录> --acceptance <验收JSON> --output <交付目录>
```

正式封包必须通过脚本 gate，不能手改 verification 造通过。只要有角色、依赖或管理组件未验收，继续完成或明确阻塞，不把暂存目录改名为正式气隙包。

## 初级工程师交接要求

检查生成的 `docs/现场操作.md` 和 `docs/Spug操作.md`。手册必须包含：目标主机角色表、安装前准备、逐项参数解释、可以复制的命令、每步成功标志和失败停止点、业务验收方式、升级前备份和恢复边界。缺少专有步骤时修改制包配置的 `site_notes` 或适配资源并重新 build、验收，不能直接修改已经计算 SHA256SUMS 的暂存包。不能要求现场工程师编写 YAML、SQL 或发布脚本。

Spug 使用自定义发布：先受控传入发行包，首次在对应主机用向导生成本地配置；后续发布选择已纳管主机，运行手册中预置的非交互命令。不要把客户密码放到发布标题、SPUG_RELEASE、命令参数或日志。若版本涉及不兼容数据恢复，手册必须引导使用已测试的 restore hook，不进行泛化自动回滚。内置 OpsKit 本体只提供安装和检查；其自身跨版本数据库迁移不混入业务发布。

交付最终 tar.gz、SHA-256、中文手册、实际验收摘要，说明适用系统与架构。保留原业务数据和未授权的本机配置，生成包排除临时数据、真实凭据及其他项目。没有执行过的验证不得写为通过。

需要独立演练时使用 [示例仓库](assets/example/README.md)，并保留它与真实客户业务的边界。
